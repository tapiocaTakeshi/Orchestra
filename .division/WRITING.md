# Orchestra UI/UX改善 仕様書（再整理版）

対象: Electron アプリ `Orchestra`  
用途: 実装・レビュー時の共通基準  
対象読者: planner / designer / coder / reviewer

---

## 0. この文書の位置づけ

本書は、Orchestra の UI/UX 改善を実装するための**参照仕様書**です。  
単なる見た目の方針ではなく、以下を一貫して定義します。

- 画面構成
- 共通コンポーネント
- 状態設計
- 操作導線
- Electron 固有の注意点
- 実装・レビュー観点

> 重要:  
> 本仕様は汎用的な改善方針をベースにしつつ、既存実装への適用を前提にしています。  
> 既存コードの技術スタック・画面構成・状態管理と矛盾する場合は、**全面置換ではなく差分適用**を基本方針とします。

---

# 1. 改善の目的

## 1.1 目的
Orchestra の UI/UX 改善により、以下を実現する。

1. ユーザーが現在位置と次の操作を理解しやすくする
2. 主要タスクの操作回数・迷いを減らす
3. 情報の優先度と状態変化を明確に伝える
4. 一覧・詳細・編集・設定の体験を統一する
5. Electron アプリとして自然な操作感を持たせる
6. 今後の機能追加に耐えられるコンポーネント構造へ整理する

## 1.2 改善対象
以下を改善対象とする。

- アプリ全体レイアウト
- ナビゲーション
- 一覧画面
- 詳細画面
- 作成 / 編集画面
- 設定画面
- モーダル / ダイアログ
- 通知 / トースト / ステータス表示
- Loading / Empty / Error / Success の状態表示
- キーボード操作 / フォーカス制御
- Electron 固有 UI 領域

# 2. 設計原則

## 2.1 基本原則
以下の原則を全画面・全コンポーネントに適用する。

### A. 明確性
- 今どの画面にいるか分かる
- 何が重要か一目で分かる
- 次に何をすべきか判断できる

### B. 一貫性
- 同じ意味のUIは同じ見た目・挙動にする
- ボタン、入力、通知、モーダルのルールを共通化する
- 画面間でレイアウトの骨格を揃える

### C. 即時フィードバック
- 処理中、成功、失敗、空状態を必ず示す
- クリック後に無反応に見える時間を作らない
- 破壊的操作には明確な確認と結果表示を行う

### D. 操作効率
- 主要アクションは見つけやすく、押しやすくする
- キーボード操作を考慮する
- 一覧→詳細→編集の導線を短くする

### E. 拡張性
- 共通コンポーネント化しやすい設計にする
- 画面固有実装を減らす
- 将来のテーマ切替・機能追加に耐えられるようにする

# 3. 画面構成仕様

---

## 3.1 全体レイアウト構成

アプリ全体の基本レイアウトは以下を標準とする。

1. **Sidebar / Global Navigation**
2. **Header / Top Bar**
3. **Main Content**
4. **Status Area / Footer（必要時）**

### 目的
- 画面切替、現在位置、主要操作、状態表示を分離する
- 情報の階層を明確にする
- ウィンドウサイズ変更時にも破綻しにくい構造にする

### レイアウト要件
- 左側: グローバルナビゲーション
- 上部: 画面タイトル、パンくず、検索、主要アクション
- 中央: 作業領域
- 下部または画面内: ステータス、進捗、補助情報

### 共通ルール
- ヘッダーは全画面で役割を統一する
- ページタイトルは1画面1つ
- 主要アクションはヘッダー右側またはコンテンツ先頭に固定する
- コンテンツ幅、余白、カラム構成を共通化する

---

## 3.2 グローバルナビゲーション

### 役割
- 主要機能への移動
- 現在地の把握
- 画面間の行き来を容易にする

### 要件
- 項目名は短く、意味が明確であること
- アクティブ状態を視覚的に明確にする
- アイコンのみではなくテキストラベルを併記する
- 必要に応じてセクション見出しを設ける
- 項目数が多い場合はグルーピングする

### 挙動
- 現在ページに対応する項目を active 表示
- hover / focus / active / disabled を定義
- 狭いウィンドウ幅では折りたたみ可能にする
- 折りたたみ時も tooltip でラベル確認できるようにする

---

## 3.3 ヘッダー

### 役割
- 現在のコンテキスト表示
- 主要アクション配置
- 補助操作（検索、フィルタ、切替など）

### 構成要素
- ページタイトル
- 説明文または補足文
- パンくず（必要時）
- グローバル検索 / コマンド起点
- 主要アクションボタン
- 補助操作（更新、絞り込み、表示切替など）

### 要件
- タイトルは視覚的に最上位
- 補助情報は主情報より弱い見た目にする
- 主要アクションは1〜2個までを原則とする
- アクションが多い場合は Overflow Menu に逃がす

---

## 3.4 ダッシュボード / 概要画面

### 目的
- 現在の状態を俯瞰する
- 次に行うべきアクションへ短く遷移させる

### 表示内容
- 主要指標カード
- 最近の活動
- 進行中タスク
- 注意すべきエラー / 警告
- クイックアクション

### 要件
- 情報は「重要指標 → 進行状況 → 最近の更新」の順で配置
- 単なる情報表示ではなく、次アクションへの導線を置く
- カードのクリック可否を明確にする
- 状態異常は色だけでなくラベルやアイコンでも示す

---

## 3.5 一覧画面

### 役割
- 複数アイテムの検索、比較、選択、操作

### 基本構成
1. ページタイトル
2. 主操作（新規作成など）
3. 検索 / フィルタ / ソート
4. 件数表示
5. 一覧本体
6. ページングまたは読み込み継続制御

### 要件
- 検索 / フィルタ / ソートは一覧直上に集約
- 行全体クリックと個別アクションを混同させない
- 選択状態を明確にする
- 項目が0件のときは空状態を表示する
- 長い一覧ではヘッダー固定を優先する

### テーブル / リスト設計
- 列見出しは明確で短いこと
- 数値や日時は比較しやすい表記に揃える
- 省略記号利用時は tooltip または詳細表示を用意する
- 危険操作は行内の目立つ位置に直置きしない
- 並び替え中 / フィルタ適用中の状態を明示する

---

## 3.6 詳細画面

### 役割
- 対象1件の情報確認
- 編集・削除・関連操作への導線

### 基本構成
1. 戻る導線
2. タイトル / 識別名
3. 状態ラベル
4. メタ情報（更新日時、作成者など）
5. 主要操作
6. セクション別詳細情報

### 要件
- 冒頭で「何の詳細か」が即座に分かる
- ステータスは目立つ位置に表示する
- 編集・削除・複製などの操作を整理する
- 情報は意味単位でセクション分けする
- 長い詳細では目次 or セクションナビを検討する

---

## 3.7 作成 / 編集画面

### 役割
- 新規作成
- 既存情報の更新

### 基本構成
1. タイトル
2. 保存状態の表示
3. 入力フォーム
4. 補足説明
5. 保存 / キャンセル

### 要件
- 必須項目を明示する
- 関連項目はグループ化する
- 保存導線は常に見つけやすい位置に置く
- 入力エラー時は問題箇所まで到達しやすくする
- 未保存変更がある場合は離脱確認する

### 挙動
- 保存中は二重送信を防止
- 保存成功時は結果を明示
- 保存失敗時は入力内容を保持
- 自動保存がある場合はそのルールを明示する

---

## 3.8 設定画面

### 役割
- アプリ全体の動作、表示、環境設定の変更

### 要件
- カテゴリごとに整理する
- 即時反映と保存反映を明確に分ける
- 影響範囲の大きい設定には説明を付ける
- 初期値復元やリセットは危険操作として扱う

### 推奨構成
- 一般設定
- 表示設定
- ショートカット設定
- 環境 / 接続設定
- 高度な設定

---

## 3.9 モーダル / ダイアログ

### 用途を限定する
モーダルは以下に限定する。

- 破壊的操作の確認
- 画面遷移なしで完結する入力
- 高い注意喚起が必要な案内

### 構成
- タイトル
- 目的説明
- 必要入力
- 主操作
- キャンセル
- 閉じる導線

### 要件
- 何を確認しているか明確であること
- 主ボタン / キャンセルの意味が明確であること
- フォーカストラップを適用
- 閉じた後は元のフォーカス位置へ戻す

### 閉じ方ルール
- ESC: 基本有効
- 背景クリック: 重要度が低いモーダルのみ許可
- 破壊的確認: 背景クリックで閉じないことを推奨

---

## 3.10 通知 / トースト / インラインメッセージ

### 用途
- 成功通知
- 軽微なエラー通知
- 非同期処理結果の通知
- 補助的なガイダンス

### 要件
- 消えて困る内容はトーストだけにしない
- 再試行可能なエラーは導線を付ける
- Success / Warning / Error / Info を視覚的に区別する
- スクリーンリーダー配慮を行う

---

- ヘッダー固定対応
- 行 hover / selected / focused を定義

- 列幅の基本ルールを定義
- 操作用セルは一貫位置に揃える

### List 要件
- クリック可能範囲を明確化
- 補助アクションは右端など一定位置に集約
- 選択状態を視覚的に区別

---

## 4.6 Modal / Dialog 仕様

### variant
- standard
- confirm
- danger

### 要件
- タイトル必須
- 説明文は簡潔に
- 主操作ボタンを明示
- 閉じたとき状態復帰を行う
- キーボードだけでも操作完結できる

---

## 4.7 Empty / Loading / Error / Success 仕様

### EmptyState
表示要素:
- タイトル
- 補足説明
- 次の行動
- 任意でアイコン / イラスト

### LoadingState
表示要素:
- スピナー or スケルトン
- 読み込み対象を示す文言

### ErrorState
表示要素:
- エラー概要
- 推奨アクション
- 再試行導線
- 必要に応じて詳細表示

### Success
- トーストまたはインラインで表示
- 成功後の次アクションを示せると望ましい

# 5. 状態設計仕様

---

## 5.1 状態設計の基本方針
UI で扱う状態は、見た目だけでなくユーザーの理解を支えるものとして定義する。

### 必須で考慮する状態
- 初期表示
- 読み込み中
- 読み込み成功
- 空状態
- エラー
- 送信中
- 保存成功
- 保存失敗
- 無効状態
- 未保存変更あり

---

## 5.2 画面単位状態

### 一覧画面
- loading
- loaded
- empty
- error
- filtering
- refreshing

### 詳細画面
- loading
- loaded
- not-found
- error
- deleting
- updating

### 編集画面
- pristine
- dirty
- validating
- submitting
- submit-success
- submit-error

### 設定画面
- initial
- changed
- saving
- saved
- save-error
- reset-confirm

---

## 5.3 非同期処理の表示ルール

### 短時間処理
- ボタン loading
- 軽量スピナー

### 中時間処理
- インライン進行表示
- ステータス文言

### 長時間処理
- 進捗表示
- キャンセル可否表示
- バックグラウンド継続可否表示

---

## 5.4 エラーメッセージ規則

エラーメッセージは以下の構造を原則とする。

1. 何が起きたか
2. ユーザーに何が影響するか
3. 次に何をすればよいか

### 悪い例
- Error occurred
- Failed

### 良い例
- 設定の保存に失敗しました。ネットワーク接続を確認して、もう一度お試しください。
- 一覧データを取得できませんでした。再読み込みするか、しばらく待ってから再試行してください。

# 6. 操作導線仕様

---

## 6.1 主要タスク導線
以下の主要フローを短く・明確にする。

1. 一覧を見る
2. 検索 / 絞り込みをする
3. 対象を選ぶ
4. 詳細を見る
5. 編集する
6. 保存する
7. 結果を確認する

### 導線原則
- 各画面で主目的を1つ定める
- 主操作は目立つ位置に固定
- 補助操作は主操作を邪魔しない配置にする
- 破壊的操作は距離と視覚差を持たせる

---

## 6.2 一覧 → 詳細 → 編集

### 一覧
- 項目選択
- 詳細遷移
- 新規作成導線
- フィルタ / ソート

### 詳細
- 編集導線
- 戻る導線
- 状態確認
- 関連情報参照

### 編集
- 入力
- 保存
- キャンセル
- 離脱確認

---

## 6.3 検索導線
- 検索入力は分かりやすい位置に配置
- 検索対象を明示
- 0件時は検索条件見直し導線を出す
- グローバル検索を導入する場合はショートカットを付ける

---

## 6.4 破壊的操作導線
- 削除やリセットは danger 表現
- 確認ダイアログで対象名を明示
- 実行後は取り消し可否を可能な限り示す
- 二重実行を防ぐ

---

## 6.5 キーボード操作
最低限以下に対応することを推奨する。

- `Tab` / `Shift + Tab`: フォーカス移動
- `Enter`: 主操作実行
- `Esc`: モーダルを閉じる、キャンセル
- `Ctrl/Cmd + S`: 保存
- `Ctrl/Cmd + K` または `Ctrl/Cmd + P`: クイック検索 / コマンドパレット

### 要件
- フォーカスリングを消さない
- フォーカス順を視覚順・意味順に揃える
- モーダル内はフォーカスを閉じ込める
- モーダル終了後は元の要素へ戻す

---

# 7. Electron 固有注意点

---

## 7.1 ウィンドウサイズ・リサイズ
- 最小サイズでも主要操作が隠れないこと
- 幅が狭い場合の折りたたみルールを定義する
- 複数カラムは段階的に1カラムへ落とせること
- スクロール領域を意図的に管理すること

---

## 7.2 カスタムタイトルバー
カスタムタイトルバー採用時は以下を守る。

- ドラッグ可能領域と操作可能領域を分離する
- `-webkit-app-region: drag` と `no-drag` を適切に使う
- 検索欄、ボタン、タブなどは必ず no-drag
- macOS / Windows でウィンドウボタン位置差を考慮する

---

## 7.3 OS ネイティブ機能との使い分け
以下はネイティブ優先を検討する。

- ファイル選択
- 保存先選択
- 通知
- ショートカット登録
- コンテキストメニューの一部

### 原則
- OS標準で期待される操作は可能な限り標準挙動に寄せる
- アプリ内UIに置き換える場合は理由が必要

---

## 7.4 IPC / バックグラウンド処理
- 処理待ちで無反応に見せない
- main / renderer の違いをユーザーに見せない
- 技術用語そのままのエラー文を出さない
- 長時間処理は進捗か状態説明を出す
- バックグラウンド完了時は通知を行う

---

## 7.5 永続化されるUI状態
以下の保持を検討する。

- ウィンドウサイズ / 位置
- 開いていたタブ
- サイドバーの開閉状態
- 一覧のソート / フィルタ条件
- 最終選択項目

### 原則
- ユーザーの作業再開を助ける状態は保存する
- セキュリティ上問題のある入力内容は慎重に扱う

---

## 7.6 プラットフォーム差異
- macOS と Windows でキー表記を出し分ける
- メニュー配置やショートカット文化の違いを考慮する
- フォントレンダリング差で崩れない余白設計にする

---

# 8. アクセシビリティ仕様

## 8.1 基本要件
- キーボードのみで主要タスクを完了できる
- フォーカス可視
- 適切なラベル付与
- 色だけで状態を伝えない
- コントラストを確保する

## 8.2 必須対応
- `button`, `input`, `dialog` などセマンティック要素を優先
- アイコンボタンに `aria-label`
- エラー文と入力の関連付け
- 通知の読み上げ配慮
- モーダルに role とラベルを設定

## 低優先

# 10. 実装・レビュー観点

## 10.1 実装チェック
- 共通UIに寄せられているか
- 状態表示が欠けていないか
- ボタン種別が乱れていないか
- 画面の主目的が明確か
- エラー時に次アクションが示されるか
- Electron 固有領域で誤操作が起きないか

## 10.2 レビューチェック
- 主要タスクが迷わず実行できるか
- 同じ操作が別画面で別挙動になっていないか
- 破壊的操作が安全に設計されているか
- リサイズ時に崩れないか
- フォーカス・キーボード操作が自然か
- 成功 / 失敗 / 空状態が明確か

---

# 11. 完了条件

以下を満たした時点で、本UI/UX改善は一定完了とみなす。

1. 主要画面のレイアウト骨格が統一されている
2. 一覧 / 詳細 / 編集 / 設定の導線が明確である
3. Button / Input / Modal / Toast などの共通コンポーネントが整備されている
4. Loading / Empty / Error / Success の状態表現が実装されている
5. キーボード操作とフォーカス制御が破綻していない
6. Electron 特有のリサイズ・タイトルバー・通知設計が考慮されている
7. 既存機能を損なわず、操作性が改善している

# 12. 後続エージェント向け引き継ぎ

## planner への引き継ぎ
- 本仕様をもとに、既存コードベースとの整合を確認した上で実装方針を差分設計すること
- 既存UIライブラリ・状態管理があれば優先再利用すること
- 新規導入が必要な場合は移行コストと適用範囲を明示すること

## designer への引き継ぎ
- 画面単位ではなく、まず共通パターンを可視化すること
- 一覧 / 詳細 / 編集 / 設定 / モーダルの5系統を優先してデザイン化すること
- 状態別デザイン（loading / empty / error / success）も必ず含めること

## coder への引き継ぎ
- `MainLayout` と共通コンポーネント群の整備を優先すること
- 画面固有実装より先に Button / Input / Modal / State Components を揃えること
- Electron 固有の drag/no-drag、ショートカット、永続化状態に注意すること

# 13. 補足方針

- 本仕様は「全部を一度に置き換える」前提ではない
- 既存画面に段階的に適用し、共通化できた単位から展開する
- 画面単位の微調整より、まずルールの統一を優先する
- 見た目の刷新のみで終わらせず、状態遷移と操作導線をセットで改善する
