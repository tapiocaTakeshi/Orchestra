# SidebarChat 変更内容ドキュメント（改訂版）

## 概要
`SidebarChat.tsx` の見た目改善は、**大規模な構造変更よりも既存コンポーネントに対する段階的なスタイル改善**を中心方針とします。  
今回の方針では、以下を重視しています。

- VS Code Webview 環境に馴染むこと
- 既存の `--void-*` / `--vscode-*` 系変数を活かすこと
- 依存追加なしで、CSS / Tailwind / 既存クラス中心に演出すること
- チャット・ツール実行・レビューの**状態差**を見た目で理解しやすくすること

---

## 採用したデザイン方針

今回採用する方向性は、提案群のうち主に以下の組み合わせです。

### 1. Glass / Card Depth 強化
既存の Void テーマを壊さず、カード感・奥行き・境界線の見やすさを強化します。

- メッセージやツール結果をカード的に整理
- 背景を単色ベタ塗りではなく、薄いグラデーションや濃淡差で分離
- hover 時に軽いボーダー変化と浮き上がり感を追加

### 2. Status-First 可視化
ツール・レビュー・思考中などの状態を、テキストだけではなく**色・線・バッジ**で補強します。

- 実行中: 青/アクセント寄り
- 成功/完了: 緑寄り
- エラー/却下: 赤 or warning 寄り
- 補助情報: muted なトーン

### 3. Ambient Motion
派手なアニメーションではなく、**最小限の動き**だけを採用します。

- hover 時のわずかなリフト
- 折りたたみ時の `opacity` / `translateY`
- loading 時の控えめな点滅・回転・パルス

## 実装方針

- `DivisionOrchestrationComponent`
- `FlowReviewComponent`
- `CommandBarInChat`
- `SelectedFiles`
- `ScrollToBottom` 系ボタン

---

## 2. 実装スタンス
今回の改善では、以下を原則とします。

- 既存コンポーネント構造は極力維持
- まず見た目の改善を優先
- 新規ライブラリ追加は行わない
- `framer-motion` は採用しない
- Tailwind クラス、既存 CSS、軽量な inline style で対応

---

## UI 演出手法の調査結果まとめ

VS Code Webview / React / Tailwind 前提で、現実的に採用しやすい演出は以下です。

### 採用しやすいもの
- `transition-colors`
- `transition-all`
- `opacity`
- `transform: translateY(...)`
- `scale`
- `shadow`
- `border-color` の変化
- `animate-pulse`
- `animate-spin`
- `max-height` + `overflow-hidden` による折りたたみ

### 注意して使うもの
- `backdrop-blur`
  - 見た目は良いが、環境によって効き方や重さに差がある
  - 必須ではなく、補助的に使う
- 大きな box-shadow
  - ダークテーマでは映えるが、やりすぎると浮きすぎる
- 常時アニメーション
  - 長時間表示でノイズになりやすい

### 採用しないもの
- `framer-motion`
  - 今回の改善規模に対して過剰
  - Webview 内での依存追加・保守コストを増やす
- 重いフィルタ演出
  - `blur()` 多用や複雑な背景エフェクトは避ける

## UX 課題分析まとめ

現状の `SidebarChat.tsx` に対して、主に次の課題があると整理します。

### 1. 情報のまとまりが弱い
- アシスタント本文
- reasoning
- ツール結果
- review
- 入力欄

これらの視覚的な区切りが弱いと、長い会話で読みづらくなります。

### 2. 状態差が見分けづらい
- 実行中
- 完了
- エラー
- 却下
- 承認待ち

がテキスト依存になりやすく、一覧で把握しづらいです。

### 3. 操作の重み付けが不十分
- 承認/却下
- 編集
- 送信
- 添付
- Accept All / Reject All

などの重要操作が、視覚的に同列に見える可能性があります。

### 4. 情報密度の制御が必要
詳細情報をすべて開いたままにすると、以下が起こりやすいです。

- 縦に長くなる
- 本文が埋もれる
- 重要な操作に辿り着きにくい

このため、折りたたみと強弱付けが重要です。

## テーマ変数対応方針

今回の改善では、独自デザイン用の値を増やしすぎず、既存のテーマ変数と対応付けて使う方針です。

## 1. 基本対応表

| 用途 | 優先利用する変数 | 補足 |
|---|---|---|
| ベース背景 | `var(--void-bg-1)` | チャット全体、入力ベース |
| サーフェス背景 | `var(--void-bg-2)` | カード、ツールヘッダー、レビュー |
| 強調サーフェス | `var(--void-bg-3)` | hover、開いたパネル、補助面 |
| 主テキスト | `var(--void-fg-1)` | 本文、主要ラベル |
| 補助テキスト | `var(--void-fg-2)` | メタ情報、説明、サブ文言 |
| 弱テキスト | `var(--void-fg-3)` | 非アクティブ、補足 |
| 基本境界線 | `var(--void-border-1)` | コンテナ枠、通常ボーダー |
| 強調境界線 | `var(--void-border-2)` | hover、開閉、選択 |
| フォーカス | `var(--vscode-focusBorder)` | フォーカス、進行中アクセント |
| 成功 | `var(--vscode-testing-iconPassed)` もしくは緑系既存色 | 成功、承認 |
| エラー | `var(--vscode-errorForeground)` | エラー、却下 |
| 警告 | `var(--vscode-editorWarning-foreground)` | 注意、保留 |

---

## 2. 独自変数とのマッピング方針
デザインモックで使っていた独自名は、実装では次のように読み替えます。

| モック上の変数 | 実装時の対応 |
|---|---|
| `--void-bg-base` | `--void-bg-1` |
| `--void-bg-surface` | `--void-bg-2` |
| `--void-bg-elevated` | `--void-bg-3` |
| `--void-border-subtle` | `--void-border-1` |
| `--void-border-active` | `--void-border-2` or `--vscode-focusBorder` |
| `--void-text-primary` | `--void-fg-1` |
| `--void-text-secondary` | `--void-fg-2` |
| `--void-text-muted` | `--void-fg-3` |
| `--void-accent-primary` | `--vscode-focusBorder` |
| `--void-success` | `--vscode-testing-iconPassed` もしくは既存 success 系 |
| `--void-warning` | `--vscode-editorWarning-foreground` |
| `--void-error` | `--vscode-errorForeground` |

## 実装ルール

### 1. 色の意味づけ
色の意味は全体で固定します。

- 青: 現在進行中 / フォーカス / 選択
- 緑: 成功 / 承認 / 完了
- 赤: エラー / 却下 / 危険操作
- 黄/橙: 注意 / 保留 / 実行中補助

### 2. アニメーションルール
- 基本は `150ms`〜`200ms`
- 常時動く演出は最小限
- 重要なのは「状態の伝達」であり、装飾ではない

### 3. 余白ルール
- 4 / 8 / 12 / 16 px 系のリズムに揃える
- カード内情報は上下左右のまとまりを優先

## 非採用事項

今回の方針では、以下は見送ります。

- `framer-motion` 導入
- 大規模なコンポーネント分割
- 重いグラスモーフィズム依存
- 装飾目的の派手なアニメーション

理由:
- 要件は「見た目の洗練」であり、まずは既存実装を活かした改善が適切なため
- 保守性と実装コストのバランスを優先するため

---

## 要約
今回の `SidebarChat` 改修方針は、**既存構造を保ちながら、カード化・状態可視化・最小限のモーションで UI を洗練する**ことにあります。  
特に重要なのは次の4点です。

1. `--void-*` / `--vscode-*` 変数に沿ったテーマ整合
2. ツール・レビュー・reasoning の状態差を視覚化
3. 入力欄とログの情報設計の整理
4. 依存追加なしで現実的に実装できること

後続エージェントは、このドキュメントを基に**実際の TSX 差分内容と対応箇所**を追記すれば、そのまま変更共有資料として利用できます。
