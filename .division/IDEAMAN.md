## ideaman（改善案の再整理）— Electron「Orchestra」UI/UX改善の論点分解（後続実装用）

> 前提：現状UIの“正確な構成”は未共有のため、**課題仮説→改善施策→優先度→実装論点**へ分解して後続（file-searcher / planner / designer / coder）が迷わない形に整えます。  
> その後、**file-searcher の実コード根拠**で“仮説の当たり/外れ”を確定する運用にします。

---

# 1. 想定課題の再整理（Electronで起きやすい“体験の崩れ”に寄せる）

## 1-1. 迷う（導線・情報設計）
- 目的（何をしたいか）に対して、画面が即座に答えない
- 設定/実行/結果/ログが混在し、次の行動が分からない
- 戻る動線・状態復元（モーダル閉じた後/詳細→一覧など）が弱い

## 1-2. 見つからない／読めない（視認性・階層）
- 見出し・ラベル・本文・重要度の階層が弱い
- 状態（Loading / Empty / Error / Success）が画面で統一されていない
- 長い一覧/テーブルで“行の追跡”ができない（選択/ヘッダ固定/追従がない）

## 1-3. 重い・遅い（Electron特有のパフォーマンス体験）
- 起動が遅い／初期表示まで待たされる
- 入力→反映の遅延（IPC/再レンダリング/重い計算）
- 大量データでスクロールがカクつく（仮想スクロール未導入など）

## 1-4. ぶれる（コンポーネント一貫性）
- ボタン種別・disabled/loading/error の表現が揃っていない
- フォームのエラー表示が揃っていない（原因/対処が分からない）
- モーダル乱用により認知負荷が上がる

## 1-5. デスクトップ操作に弱い（キーボード・フォーカス）
- Tab順序、フォーカス復元、ESC挙動、ショートカットがない
- テーブル/リストでキーボード操作が成立しない

---

# 2. 改善施策の“束”（後続が実装単位にできる粒度）

以下を「UI改善チケット」として切り出せるよう、施策を束（テーマ）で定義します。

## 束A：共通ステータスUIの導入（最優先候補）
- Loading / Empty / Error / Success を共通コンポーネント化
- 長時間処理は進捗＋キャンセル（可能なら）または“待ってOK”の明示
- 失敗時は「原因概要→修正導線→再試行」を必ず表示

**成果物（後続へ）**
- `StatusCard` / `InlineAlert` / `Toast` / `ProgressBar` の仕様
- 各画面の状態遷移表（例：取得中→成功→一覧表示、失敗→再試行）

## 束B：画面骨格の統一（レイアウト/情報設計）
- Orchestraの方針に沿って固定骨格：
  - Header（画面名＋主アクション＋検索/絞り込みが必要なら集約）
  - Sidebar or Tabs（画面遷移）
  - Content（作業領域）
  - Footer/Statusbar（ログ/進捗/ショートカットヒント）
- 画面内の“区画”を明確化（プライマリ操作の置き場を固定）

**成果物**
- `MainLayout` / `SectionHeader` / `PageHeader` のテンプレ定義
- “設定系”と“実行系”の視覚/構造分離ルール

## 束C：入力・フォーム体験の統一（バリデーション）
- ラベル/必須/ヒント/エラーの配置規則
- バリデーションタイミング統一（入力中/フォーカスアウト/保存時）
- 保存ボタン位置の固定、二重送信防止、未保存変更の扱い統一

**成果物**
- `FormField` / `ValidationMessage` の共通仕様
- フォーム状態：pristine/dirty/submitting/error のUI

## 束D：一覧/テーブルの“追跡性”改善
- ヘッダ固定 or 視認性確保
- 行選択/現在行のハイライト統一
- 検索・フィルタ・ソートを一覧の直上へ
- 選択→詳細表示（遷移 or サイドパネル）を決めて統一

**成果物**
- `DataTable` / `VirtualizedList` の方針（仮想スクロール要否基準）
- 行クリックの挙動仕様（詳細開く/編集モード/選択のみ など）

## 束E：モーダル/通知の設計見直し（認知負荷）
- モーダル適用は限定（破壊的操作・重要確認・簡易設定だけ）
- モーダルにフォーカストラップ、ESC/外側クリック挙動ルール
- 通知（Toast）に必要なら「詳細/再試行」導線

**成果物**
- `ConfirmModal` / `ActionModal` / `Toast` の設計規約

## 束F：デスクトップ操作最適化（キーボードファースト）
- フォーカスリング視認性、Tab順序、フォーカス復元
- ESCでモーダル閉じる/フォーカス戻す
- 主操作のショートカット（コマンドパレット含む）を設計

**成果物**
- `ShortcutMap`（どの画面で何が効くか）
- フォーカス復元の要件（閉じたらどこへ戻す）

## 束G：Electron体験の底上げ（性能×体験）
- 初期表示までの遅延対策（遅延ローディング/スケルトン）
- 大リストの仮想スクロール
- アニメはCSS優先、レンダリング過多を避ける
- IPCでブロックしない（必要なら進捗UI）

**成果物**
- “体験として遅い”箇所の計測観点（起動/入力遅延/スクロール）

---

# 3. 優先度（実行順）— “最短で体験が良くなる”順

> file-searcherで画面・データ規模が分かり次第、優先度は微調整します。

## P0（最初の一歩で体験が変わる）
1. 束A：共通ステータスUI（Loading/Empty/Error/Success）
2. 束B：画面骨格の統一（Header/Sidebar/Content/Status）
3. 束F：フォーカス・ESC・キーボード基本動線（壊れやすいので早期に）

## P1（次に業務効率に効く）
4. 束D：一覧/テーブルの追跡性（仮想スクロール含む）
5. 束C：フォームUI（バリデーション/保存体験）

## P2（質の仕上げ・認知負荷の削減）
6. 束E：モーダル/通知ルール統一
7. 束G：性能最適化（“測ってから直す”）

---

# 4. 後続エージェントへ渡す“論点”チェックリスト（最重要）

## 4-1. file-searcherが出すべき情報（仮説確定用）
- 既存の画面一覧（ルーティング単位）
- 各画面で使っているUIライブラリ（例：MUI/Antd/Radix/Tailwindなど）
- 状態管理（Zustand/Redux/ローカルstate）と、IPC/非同期処理の位置
- 既存のコンポーネント構成（Button/Input/Modal/Toast の有無）
- 大リストの規模（最大行数）とレンダリング方法（仮想スクロール有無）

## 4-2. plannerが判断すべき技術/方針の意思決定項目
- 既存スタックと、Tailwind/Radix/Zustand等の方針が“競合 or 追加で済む”のどちらか
- デザインシステムの最小セット（Button/Input/Modal/Toast/Status/Empty/Error）
- 一覧→詳細の遷移形式（ページ遷移/サイドパネル/モーダル）統一方針

## 4-3. designerがモックで必ず含めるべき画面状態
- Loading（スケルトン/スピナー）＋文言
- Empty（理由＋次のアクション）
- Error（原因概要＋再試行）
- Success（Toast/インライン＋次導線）
- フォーカス状態（キーボード操作時の見え方）

## 4-4. coderが実装で失敗しやすいポイント（事前合意用）
- フォーカストラップ/ESC/フォーカス復元を“共通部品”に持たせるか
- 状態遷移（特にエラー時）でフォーム入力を保持するか破棄するか
- 大リストでのパフォーマンス（仮想スクロール導入条件）
- IPCが遅いケースのUX（UI側で“待ってOK”を作る）

---

# 5. “この改善をOrchestraとしてどう表現するか”の指針（まとめ）

- **見た目刷新より先に**：状態UIと骨格（束A/B）で“安心して操作できる”状態を作る  
- **次に**：一覧・フォーム（束C/D）で“作業が速くなる”体験へ  
- **仕上げ**：モーダル/通知（束E）で認知負荷を減らし、性能（束G）で“気持ちよさ”を整える  
- **常に**：デスクトップ操作（束F）を前提に設計する

---

## 後続への依頼（ideamanから最初に動いてほしい順）
1. **file-searcher**：現コードの画面/コンポーネント/状態/ライブラリ根拠を出す（仮説確定）
2. **planner**：既存スタックと衝突しない範囲で、最小Design System（Button/Input/Modal/Toast/Status）を確定
3. **designer**：上記束A/B/C/D/E/Fに対応した“状態付きモック”を画面単位で作成
4. **coder**：Layout + Baseコンポーネント群（Status/Buttons/Inputs/Modal/Toast）から実装開始

必要なら、file-searcher の実出力を受け取った後に、この優先度と束を「Orchestraの実画面名」に合わせて再マッピングします。
